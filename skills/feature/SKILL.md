**Offer first (model-invoked entry).** If you entered this lane by matching the conversation — not a typed `/friday:feature` — offer it before any work: “That's new scope on a delivered project — run `/friday:feature` to take it through discovery and a scaled build?” Wait for an explicit yes; a declined offer does nothing and spends nothing.

You are the lead running `/friday:feature` — a mini-one-shot against a TSOW slice: incremental growth through the same discovery→build→synthesis recipe, scaled down.

**Lane entry, before anything else: set up the live progress list (INC-205).** Break the lane's arc — discovery through close — into the harness's live task list, scaled to the slice with **no minimum size** (a three-item slice gets a three-item list; "too small to bother" is exactly the judgment that rationalises the step away — INC-205 D4); what goes on it is your judgment (D2). Plan up front and keep it true per `docs/teammate-contract.md` § Compaction continuity #1 — the rule's single home, and it binds you: items marked finished as they land, one in progress at a time, because a stale list misdirects crash recovery — recovery is told to trust the list. Session list, never a file tree. No task-list facility → say so once and proceed.

### Phase 1: Increment discovery (the same ceremony as bootstrap, scoped — never skipped)

A new feature is a new requirement entering the system; it gets the same heavy front the project got. **You do not interpret the ask and codify your own understanding** (DF-022 — "almost no back-and-forth" is the recorded failure mode; decide-then-ratify is pretend front-loading). Spawn `friday-brainstormer` (model: **opus** — named explicitly, never inherited), telemetry via the single primitive: `python3 "${CLAUDE_PLUGIN_ROOT}/tools/spawn_telemetry.py" --emit spawn|accept|done --agent friday-brainstormer --phase feature:increment-discovery`. Spawn message carries: the PM's ask verbatim, the TSOW path, `docs/DECISIONS.md` + the synthesized architecture set as read-first context (the system exists; it grills about the *change*, not the project), the output path and number — `docs/increments/INC-<nnn>.md`, allocated inside this machine's range (D-0113 — next id allocates inside this machine's configured range: `git config friday.id-base`), zero-padded file (`INC-001`), dotted IDs on the unpadded number (`1.m`) — the rest of the skeleton composed from the briefing template (`${CLAUDE_PLUGIN_ROOT}/docs/dispatch-briefing-template.md` — composed from the file, never from memory: a reassembled briefing drops pieces silently, and every briefing on disk before INC-208 was missing one), saved at dispatch with `--prompt-file`, and this lane's own slice of that skeleton (`${CLAUDE_PLUGIN_ROOT}/skills/feature/increment-discovery-brief.md` — the read-first list, the output shape, the authoring rules that reach zero subagents, and what is not the helper's call). Relay the grilling dialog faithfully — the non-proceed gate, one-way-door teach-backs, and second-PM-read bind exactly as at bootstrap. When the ask collides with a recorded prior stance — a spec out-of-scope item, a `non-goal:` claim line, a past decision — the collision is surfaced as dated context with the trade-off on the table, never as a bar: the rule's whole shape, including what is barred after the PM decides, lives at `docs/teammate-contract.md` § One-way-door gates (INC-206). **Nothing is codified until the grilling completes.**

The increment oracle is a SEPARATE document (DF-023): `docs/increments/INC-<n>.md`, its own scaled spine — problem/why-now, in/out scope, criticality mark, dotted requirement IDs (`FR-n.m` / `AC-n.m` / `S-n.m`, globally unique; `verify_coverage.py` closes over TSOW + increments), known-hard pins where real. `docs/TECHNICAL_SOW.md` gets exactly ONE appended line under `## Increments`: `- INC-<n> — <title> → docs/increments/INC-<n>.md (approved <date>)` — a pointer, never the spec. The TSOW stays bounded; the body stays the untouched oracle (PROP-060c). The gate is the PM approving the WRITTEN increment file — their own read, not your summary.

### Phase 2: Mini one-shot

Build the slice in this context, under the full `/friday:build` Phase-2 rules (two-channel `DECISIONS.md` capture, floor override, selective TDD on any logic-core the slice adds, hands-on verification). The TSOW is never edited beyond that single pointer line, and the increment file is oracle-frozen once approved — drift goes to `DECISIONS.md`, exactly like the TSOW body. The lightest slice still leaves an audit trail: at minimum its decision entries + journal events — "too small to record" is never a reason for zero record (ISSUE-004's lesson).

### Phase 3: Re-synthesize + close the slice

1. `/friday:reference` — re-extract, re-synthesize the touched sections (regenerate-via-git-diff), diff oracle clean.
2. Coverage — two hands, split by what the evidence IS (D-0145). **Lines whose evidence is a committed test** you append yourself, naming the test — the close's suite re-run is their verification, and a second runner watching green tests pass again buys nothing; they carry `(lead-authored)` and the reconcile cross-check of them is trivially cheap (the evidence re-runs). **Lines resting on reading and interpretation** — a grant narrowed, a dispatch shape, a doc claim, anything no pytest exercises — are NOT yours to grade: the builder misreading a requirement writes tests that encode the same misreading, so green cannot catch it. Spawn **`friday-tester`** (model: **sonnet** — named, never inherited; telemetry: `python3 "${CLAUDE_PLUGIN_ROOT}/tools/spawn_telemetry.py" --emit spawn|accept|done --agent friday-tester --phase feature:coverage`), scoped to exactly those IDs: its spawn message carries the increment file path, the judgement-set ID list with your proposed disposition for each, the rest of the skeleton composed from the briefing template (`${CLAUDE_PLUGIN_ROOT}/docs/dispatch-briefing-template.md` — composed from the file, never from memory: a reassembled briefing drops pieces silently, and every briefing on disk before INC-208 was missing one), saved at dispatch with `--prompt-file`, the explicit Read list, and its compaction drawer path. It re-verifies each in fresh context — the requirement's own words against the delivered artifact, real output quoted — and writes those lines itself tagged `(independently-tested)`; an ID it cannot confirm comes back as a finding, never a coin-flip line (role contract: `agents/roles/tester.md` § increment-scoped coverage). Only lines inside the FRIDAY-DISPOSITIONS block count — `verify_coverage.py` closes over TSOW + increments.
3. **Blast-radius check:** if the slice touched a floor category or a shared primitive, run `/friday:harden` scoped to the increment (post-incremental hardening is exactly what that command retains it for); otherwise the release-gate suite re-run + Layer-1 claim audit suffices.
4. Write the change trail `docs/trails/INC-<n>.md` in the change-trail grammar (contract: `docs/contracts/change-trail.md` — the INC trails to date existed by the lead's habit; this is the named step that makes the contract's feature-producer claim true). Re-stamp liveness on touched records. Then flip the record dirty — the slice landed on a project whose record still claims it was verified: `python3 "${CLAUDE_PLUGIN_ROOT}/tools/state_record.py" --mark stale --root .` (quiet no-op unless the project is closed; `last-verified:` untouched by design, and only a clean `/friday:reconcile` clears it — D-0106, contract: `docs/contracts/state-record.md`).
5. **Close the source proposal (pipeline projects only).** If the increment's ask arrived as a proposal (`PROP-<nnn>` — friday's self-build), the close moves its own source: `python3 tools/proposal_pipeline.py move --name PROP-<nnn> --to 03-pending-validation --root .`, and reports the move — built is not proven, so EVERY finished build lands in `03-pending-validation` first (stages and legal moves: the pipeline README in the repo that carries it). Then the hard step the close cannot complete past: `python3 tools/proposal_pipeline_check.py --root .` must print `clean`; a finding blocks the close and names its own one-command remedy (a named checklist step, the recorded deliberate exception to the fail-open guard doctrine). An increment that consumed no proposal skips the move as the defined no-op; a project with no `proposals/` pipeline skips this step entirely.
6. **Correct the project's claim record (INC-206).** Where the increment's `## Non-goals reversed` section names a reversed stance with a matching `non-goal:` claim line in the project `CLAUDE.md`'s claims block, strike that line — or narrow its wording where only part of the stance was reversed. Its own close move, deliberately not folded into step 4's stale flip. The audit trail is the increment's reversal section plus `DECISIONS.md`, never an annotation in the claim block — an annotated non-goal line still reads as a live non-goal to everything that parses it. The reversal section names which line was struck or narrowed, or states that none corresponded — the matching is a judgment made on the record, never silent (KH-4). Defined no-op: an increment that reversed nothing, or reversed a stance no claim line expresses, skips the strike and says so at close in those terms.
7. **Account for the briefings this lane actually sent (INC-208).** `python3 "${CLAUDE_PLUGIN_ROOT}/tools/dispatch_briefing_check.py" --root .` reports any dispatch whose briefing was never saved, carries no typed line, or omits a required field. **Report only — it exits 0 whatever it finds and can never be the reason a close fails**; the point is that a dropped piece becomes visible instead of silent, which is exactly what did not happen to the two defective briefings sitting on disk when this step was written. What it names, you fix now rather than batching (the composing habit is what this step protects).
8. Commit (never push).
